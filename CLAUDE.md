## What this is

Android local audio/video player (`com.abei.splitplay`). The differentiator (see `docs/PRD.md`) is **independent audio and video playback/output paths**: same file fed to separate players, audio routed to a chosen output device while video goes to a chosen display, with transparent HW/SW decode control. A planned v2 (`docs/PRD-v2.md`) layers a video-based language-learning mode on top.

**Current state** (rough mapping to the v1 roadmap):
- **M0 / M1 done** — multi-module scaffold + single-player video MVP (ExoPlayer)
- **partial M2 / M5 / M9 landed out-of-order** — the engine layer was refactored ahead of schedule to drop the Media3 `Player` from the public interface (so non-Media3 backends like IjkPlayer or a custom engine fit the same shape), `CacheDataSource` streaming cache went in without waiting for FFmpeg, and Picture-in-Picture shipped with the player UI
- **Out-of-roadmap features shipped**: MediaStore gallery, CameraX video recorder (1080p ViewPort + tap-to-focus + exposure slider + EIS auto-enable + GL beauty effect + TAP/HOLD record-button modes), **MediaPipe-driven AR gesture overlay** (single-hand thumb+index pinch → 3D geometry position/size/roll; two render modes: HUD-only Compose Canvas vs in-recording GL second pass; 21-point hand skeleton debug overlay), settings dialog (engine selector + server URL), full gesture player (swipe-to-dismiss, multi-tap ±10s, edge-hold 2×), fullscreen aspect-ratio override menu, resume position persistence

`docs/` is the authoritative spec but **partially stale vs the code** — when in doubt, the code is the truth. The "实施快照" section at the end of `ROADMAP.md` and the "v1.1 实施偏离" section in `DESIGN.md` track the deltas. Read the relevant ROADMAP section before implementing a feature — it still names the right classes, APIs, and acceptance demo for milestones that haven't been touched yet.

## Build & test

Gradle wrapper; on Windows use `.\gradlew.bat` in place of `./gradlew`.

- Build debug APK: `./gradlew :app:assembleDebug`
- All unit tests: `./gradlew test` (debug variant: `./gradlew testDebugUnitTest`)
- Single test class/method: `./gradlew testDebugUnitTest --tests "com.abei.splitplay.SomeTest"` (append `.methodName` for one method)
- Instrumented tests (needs device/emulator): `./gradlew connectedDebugAndroidTest`
- Lint: `./gradlew lint`

Toolchain: AGP 9.2.1, Kotlin 2.1.0, JVM target 11, minSdk 24, targetSdk 36, compileSdk 36.1.

## Module architecture

Four Gradle modules (root project name is `SplitPlay`):

- **`:media`** — playback engine, the heart of the app. Defines `PlayerEngine` (interface, **does not expose Media3 `Player`**, only `fun setVideoSurface(Surface?)`) + `PlaybackState` (immutable data class). `SinglePlayerEngine` is the Media3 implementation; `PlayerEngineFactory` + `PlayerEngineRegistry` route between three types (`EXOPLAYER` real, `IJK` stub, `CUSTOM` stub) so the engine kernel is pluggable. `MediaCache` is a process-singleton `SimpleCache` + `CacheDataSource` wiring for progressive HTTP streaming with on-disk caching — no local proxy. Per the original roadmap M2 split into Audio/Video engines and M5 added a `:native` module for self-compiled FFmpeg software decode; both are still TODO.
- **`:core`** — domain + persistence layer. Holds DataStore-backed `ResumeStore` (per-URI resume position) and `EnginePrefs` (selected engine + server base URL). No Media3 dependency on purpose.
- **`:player-ui`** — Compose video player UI (PlayerScreen, PlayerViewModel, PlayerSettings) as a reusable Android library. Pulls Compose, Material3, and lifecycle-viewmodel-compose into itself via `api`/`implementation` so other apps can drop in just this module + `:media` + `:core`. Depends on `:core` + `:media`.
- **`:app`** — Compose root: `MainActivity`, `AppNavHost`, gallery (`VideoGalleryScreen` + ViewModel), camera recorder (`CameraRecorderScreen` + `CameraRecorderViewModel` + `feature/camera/beauty/` — `BeautyEffect` `CameraEffect` wrapping `BeautySurfaceProcessor`, EGL14 pipeline that now runs **two passes**: OES single-pass beauty shader + optional 3D mesh second pass with depth buffer + `feature/camera/ar/` — MediaPipe `GestureRecognizer` via `HandLandmarkerAnalyzer` (separate `ImageAnalysis` UseCase), `GestureStateMachine` (single-hand pinch → `GeometryState`), `Renderable` abstraction + `BoxRenderable`, `GeometryOverlay` Compose Canvas wireframe renderer, `HandSkeletonOverlay` debug layer). Depends on all three above. CameraX is an app-level dep, not a `:player-ui` dep.

Add dependencies only via `gradle/libs.versions.toml` and reference through `libs.*` aliases — do not hardcode versions in `build.gradle.kts`. Note (documented in the toml): AGP 9.x has built-in Kotlin support, so **do not apply `org.jetbrains.kotlin.android`** — it conflicts with the auto-registered `kotlin` extension. The `kotlin` version is still consumed by the Compose compiler plugin.

**IjkPlayer note**: `IjkPlayerEngineFactory.create` currently throws `NotImplementedError` — the bilibili maven repo is unreliable, the deps are commented out in `:media/build.gradle.kts` and `libs.versions.toml`. Re-enable steps live in the factory's KDoc. The selector UI still lets users pick it; `PlayerViewModel.createEngine` catches and falls back to ExoPlayer for the session without overwriting the pref.

## Patterns & conventions

- **State flow**: `PlayerEngine.state` is a `StateFlow<PlaybackState>`. ExoPlayer pushes most changes via a `Player.Listener`, but **position does not push** — `SinglePlayerEngine` polls it on a coroutine loop (250ms) while playing. Preserve this when extending the engine.
- **MVVM**: ViewModels are `AndroidViewModel` exposing a read-only `StateFlow` of a single `<Screen>UiState` data class. Two shapes are in use: a backing `MutableStateFlow` updated via `.copy()` (gallery), and `combine(...).stateIn(...)` over several sources (player). Either is fine; match the screen's existing one.
- **Screens are stateless**: Composables take event lambdas (`onVideoClick: (Uri) -> Unit`, `onBack`); navigation decisions live in `app/.../navigation/AppNavHost.kt`, not in screens. Routes are centralized in the `Routes` object; URIs are URL-encoded into route args and decoded in the `composable` block.
- **Feature layout**: app-only screens live under `app/.../feature/<name>/` as `<Name>Screen.kt` + `<Name>ViewModel.kt` (currently `gallery/`, `camera/`). Player UI is in `:player-ui` instead of `app/feature/player/` — it's an Android library, package is `com.abei.splitplay.playerui`.
- **Engine instantiation**: `PlayerViewModel` reads `EnginePrefs.engineType` via `runBlocking { ... .first() }` in init (DataStore single-key read is constant-time once warm) and routes through `PlayerEngineRegistry.factory(type).create(app, scope)`. Catches `NotImplementedError` and falls back to `ExoPlayerEngineFactory` for the session **without rewriting the pref** — keep this fallback semantics if you swap factories.
- **Video output**: The engine does NOT expose a Media3 `Player`. The Compose-side `EngineSurface` composable wraps `SurfaceView` and calls `engine.setVideoSurface(holder.surface)` on `surfaceCreated` / `null` on `surfaceDestroyed`. Don't reintroduce `PlayerSurface(player)` — that would re-couple to Media3 and break the IjkPlayer/Custom paths.
- **Aspect ratio**: detail page is hard-wired to `VideoFitMode.FIT_AUTO`. Fullscreen reads `state.fitMode` (user-overridable via the AspectRatio menu in the top row). The helper `fitModifier(mode, videoW, videoH)` is what produces the `Modifier.aspectRatio(...)` — pass it to `EngineSurface`, not `Modifier.fillMaxSize()`, or the video will stretch.
- **Resource lifecycle**: release the `ExoPlayer`/engine in the ViewModel's `onCleared()`. `MediaCache.release()` is currently never called (single-process, single-activity); reuse the singleton across player sessions.
- **SAF permissions**: when accepting a user-picked `Uri`, call `takePersistableUriPermission` so access survives restarts (wrapped in `runCatching`). Only valid for `ACTION_OPEN_DOCUMENT` URIs (`DocumentsContract.isDocumentUri` gate) — MediaStore / PhotoPicker URIs throw `SecurityException` on the same call.
- **Nav transitions**: the `Routes.PLAYER` composable sets `EnterTransition.None` / `ExitTransition.None` / `popEnterTransition.None` / `popExitTransition.None`. The default 700ms fade makes the SurfaceView visibly flash on enter/exit because the surface attaches before the player binds. Keep transitions off for any route that hosts a SurfaceView.
- **Camera effect lifecycle**: `BeautyEffect` owns an EGL context + GL thread, so it must be created ONCE per screen via `remember` and released in `DisposableEffect.onDispose { effect.release() }`. Do NOT re-`remember` per `useFrontCamera` rebind — the same effect instance is reused across rebinds via `UseCaseGroup.Builder().addEffect(...)`. Recreating it leaks EGL.
- **Camera quality knobs**: Preview defaults to a small resolution unless you set a `ResolutionSelector` (~640×480 → blurry full-screen). Always pair `ResolutionSelector(1080×1920, FALLBACK_CLOSEST_HIGHER_THEN_LOWER)` on `Preview` + a 9:16 `ViewPort` in a `UseCaseGroup` so Preview and `VideoCapture` share one cropped stream ("what you see is what you record"). EIS is per-camera capability — query via `Preview.getPreviewCapabilities(CameraInfo).isStabilizationSupported` and `Recorder.getVideoCapabilities(CameraInfo).isStabilizationSupported` (CameraX 1.4 moved these off `CameraInfo`); failing to gate the `setXxxStabilizationEnabled` calls throws `IllegalArgumentException` at `bindToLifecycle` on unsupported cameras (commonly the front one).
- **Camera flip during recording is locked on purpose**: `LaunchedEffect(useFrontCamera)` rebuilds the `Recorder` + `VideoCapture` and calls `provider.unbindAll()`, which finalizes the active `Recording`. Path-A workaround (persistent VideoCapture + `Recording.pause/resume`) was tried and reverted — CameraX 1.4.1 still source-inactive-finalizes on some devices. Flip button is `enabled = recording == null`. If you really need mid-recording flip later, the supported path is `Recording.stop()` → start a new file → stitch with `MediaMuxer`.
- **AR SSOT**: `CameraRecorderScreen` is the one screen that DOES have a ViewModel — `CameraRecorderViewModel` holds `geometryState`/`renderMode`/`handFrame`/`showSkeleton` `StateFlow`s. Compose overlays (`GeometryOverlay`, `HandSkeletonOverlay`) and the GL second pass (via `BeautyEffect.updateGeometryState`) both consume the same `GeometryState`. Camera / Recorder state still lives in the Composable (those are tightly coupled to CameraX lifecycle, no benefit to migrating).
- **AR render mode**: `RenderMode.HUD_OVERLAY` (default) only draws the geometry in Compose Canvas — does NOT appear in recorded video. `RenderMode.IN_RECORDING` flips `BeautyEffect.setRenderGeometryEnabled(true)` which makes the GL second pass draw the mesh into the shared Preview+VideoCapture surface ("what you see is what you record"). The skeleton overlay is **always** Compose-only and never in the recording. Toggle is disabled while `recording != null` to avoid mid-video visual jumps.
- **Hand gesture pipeline**: `ImageAnalysis` UseCase joins the same `UseCaseGroup` as `Preview`/`VideoCapture` (KEEP_ONLY_LATEST + RGBA_8888 + 720p ResolutionSelector). It shares the 9:16 `ViewPort` on purpose — MediaPipe sees the same cropped frame the user sees, so landmark coords [0,1] map directly to display [0,1]. `HandLandmarkerAnalyzer` handles rotation via MediaPipe's `ImageProcessingOptions` and front-camera mirror by manually flipping landmark X + swapping LEFT/RIGHT handedness. GPU delegate is tried first, falls back to CPU; missing model file logs warn and the analyzer no-ops (UI never crashes).
- **MediaPipe model asset**: `app/src/main/assets/gesture_recognizer.task` must exist for gestures to work. Download from MediaPipe Gesture Recognizer docs. `androidResources.noCompress.add("task")` in `app/build.gradle.kts` prevents aapt from re-compressing it (would break mmap).
- **GL second pass**: `BeautySurfaceProcessor` EGL config now requests `EGL_DEPTH_SIZE = 16` (all surfaces get a depth buffer, ~4MB extra at 1080p). The first pass (beauty quad) disables depth test and clears both color+depth; the mesh pass enables `GL_DEPTH_TEST` + `GL_LEQUAL`, draws semi-transparent triangle faces then opaque line wireframe. Mesh data is client-side `FloatBuffer`/`ShortBuffer` (no VBOs — GLES2 friendly, no significant cost at 8 verts × 12 lines).
- **Coordinate convention for AR**: `GeometryState.positionNorm` is in Compose screen space (X right, Y **down**, [-1..1]) because that's what the Composable layer needs natively. The GL pass flips Y (`worldY = -positionNorm.y * halfH`) AND negates the roll angle (`Matrix.rotateM(..., -rotationDegRoll, 0, 0, 1)`) to make the on-screen rotation direction match user wrist twist consistently across both renderers. If you ever change one side, change both.
- Explicit imports (no wildcards), 4-space indent, trailing commas. Some user-facing strings are Chinese.
